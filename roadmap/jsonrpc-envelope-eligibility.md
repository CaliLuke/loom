# JSON-RPC envelope response eligibility (#676)

Owner: JSON-RPC runtime envelope classification. Parent: `182a5cc8d`.
HTTP already replies to invalid ID-less envelopes; SSE and WebSocket infer a
notification from ID absence before establishing that the envelope is valid.
The shared `invalidRequest` owner must also own the notification predicate.
Framing remains transport-specific; generated adapters only receive admitted
requests. No new DSL or transport fallback is needed.

   Assert error code, correlation and dispatch eligibility; retain following
   valid WebSocket messages and existing transport failure identity controls.
2. Model response eligibility alongside the existing notification-completion

3. Obtain independent readiness review, then centralize the predicate beside
   envelope validation. HTTP request/batch paths and stream protocol errors and
   observation derive it from that owner. Do not change generated typed payload
   validation, existing valid-envelope ID correlation, or GET listener semantics.
4. Run focused matrix and complete JSON-RPC runtime race suite; run existing
   generated notification completion and ordinary controls with local source.
   No generator source changes or intended generated byte differences. Existing
   generated integration compiles/mounts real adapters to verify the runtime seam.
5. Document valid-envelope notification semantics in public guidance and consumer
   skill; clarify the old model's admitted-request assumption. Exact final diff
   review, atomic commit, push and ticket closure follow successful checks.

The JSON-RPC 2.0 specification defines a notification as a Request object without
an ID; an invalid request receives -32600 with null when no ID is recoverable.
See https://www.jsonrpc.org/specification sections4.1,5 and7. This correction
preserves supplied valid IDs and request-local service/params failures.
