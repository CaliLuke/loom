## Established owner defect

`expr.HTTPEndpointExpr.Finalize` discovers ID only after transport bodies have
been prepared. `http/codegen` therefore emits ID as a params member, validates
that member and applies conversion defaults. JSON-RPC handlers then overwrite
it with the envelope ID without validation. The ID has competing body and
protocol ownership. Client encoders serialize both copies.

The canonical request source is `jsonrpcRequestPayload`, including WebSocket
stream normalization. The existing wire-binding owner runs before validation
and body derivation. Its envelope binding should retain logical source and
resolved attribute, while codegen resolves actual storage/name once. Shared
request decoding must normalize/admit/validate the envelope value before
constructing the service payload. Unary/SSE/WebSocket handlers consume that
payload without injection. Body extraction and outbound encoding consume the
same binding. No consumer-specific ID patches.

## Contract ledger (investigation)

Settled: ID maps the envelope to a String field; numeric tokens normalize to
strings without losing the original echo token; absent envelope ID is a
notification; replies echo original ID; optional nil/empty generated HTTP
client IDs omit the envelope ID. Required IDs must not require params copies.
Other params constraints remain independent. Result-ID policy is unchanged.

Root confirmed this composition from `presence-application-owner.md` and
`value-contract-design.md`: `id:null` is a request with original null echo, but
nonnullable String rejects it as invalid params. Nullable String retains null;
it cannot default. Missing optional ID may default in service data, without
turning the notification into a request. Required absence rejects before default
and invokes no service; notifications still have no response. Empty String is
supplied and undergoes its constraints. The existing HTTP client empty-ID
notification rule remains, as do runtime-generated WS request IDs.

Reject non-string ID types, duplicate envelope sources and explicitly competing
header/query/cookie/selected-ID-body mappings in the shared expression owner.
Named String aliases remain compositional; do not blanket-reject custom Go
storage or Nullable just because the current injection assumes native pointers.
A similarly named ordinary params member is not an envelope ID. Explicit body
objects must not contain the marked source; `Body("value")` is an ordinary valid
independent selection. Nested marked IDs need explicit rejection because the
protocol has one top-level binding and the current field selector is top-level.
No result-side policy changes or new public question are needed.

## Alternatives to test

1. Current: validate params then overwrite ID — validates the wrong value.
2. Handler-only validation — retains duplicate body membership/defaults and
   bypasses direct decoder callers.
3. Merge envelope into params JSON — loses explicit-body shapes, custom codec
   semantics and the single wire-location contract.
4. Shared envelope binding — params excludes ID; preserve envelope presence,
   normalize once, validate the actual normalized value, then construct payload.

## Concrete owner design

1. Resolve a request envelope binding in `expr` from the canonical message source
   before validation/body derivation. It retains the logical source, effective
   attribute, required/nullability semantics and envelope wire location. The
   wire-binding admission owner diagnoses duplicate or competing locations.
   Finalization must preserve the binding through server-stream normalization.
   Inferred and streaming body construction exclude the source and its required
   annotation without mutating the service payload. Explicit bodies are checked
   against that binding rather than silently deleting authored members.
2. Carry that record through transport IR to one HTTP/JSON-RPC request analysis
   record. Resolve actual `GoifyAtt` identity and `ServiceFieldLayout` storage;
   replace the current `Goify(name)` plus requiredness-only pointer guess.
   Reuse field validation, representation and conversion/default machinery.
   No hand-written native-pointer, default, Nullable or external-codec policy.
3. The shared request decoder normalizes the original envelope value into the
   proper decoding carrier, retains absent versus null, admits required/null
   before materialization, validates the normalized value and supplies the
   constructor argument. The binding is available when params is absent/empty,
   or selected as a scalar; do not merge envelope JSON into params. Remove
   `writePayloadIDInjection` from every handler. Direct decoder users receive
   the same validated ID as unary, SSE and WebSocket handlers.
4. Client body projection excludes the marked field for unary/SSE and WS.
   Preserve generated WS IDs in `WebSocketClientStream`; generated Send projects
   params before passing them to that runtime. Its current raw-service-value
   bypass must consume the same request projection, without a separate omission
   policy. ID-only payloads still get their service ID encoded even when no body
   remains; consolidate the minimal bodyless encoder with the same ID decision.
   CLI construction must retain an independent ID source after body exclusion.
   Nullable outbound null uses an explicit null token; it is not absence.
5. Keep original `RawRequest.HasID`/`ID` unchanged for notification suppression
   and error/final-response echo. Constraints and defaults alter service data
   only. Existing body constraints, security source mappings, configured codecs,
   result IDs and request correlation ownership remain independent.
